# London listings

Collects upcoming film screenings, gigs, theatre, comedy and dance from 55
London venues into one
`listings.json`, deduplicated and sorted by start time. A GitHub Action rebuilds
it every day at 06:00 London time and publishes it to GitHub Pages, along with
`status.json` (how each venue did) and a small index page.

- Data: `https://kabirhusain.github.io/london-listings/listings.json`
- Health: `https://kabirhusain.github.io/london-listings/status.json`

How each venue is collected, and why, is in `20261024_venue_survey.md` and in
each venue module's docstring.

## Running it

```bash
pip install ".[dev]"
python -m listings collect                         # all venues -> listings.json
python -m listings collect --venue ica -o out.json
python -m listings collect --status status.json    # also write status.json
python -m listings list-venues
python -m listings check-manual                    # validate manual/ files
python -m listings probe URL                       # look for JSON-LD / feeds / ticketing platform
python -m pytest -m "not network"                  # offline tests
python -m pytest -m network                        # live test per venue (~15 min uncached)
```

All requests go through `listings/http.py`. It:
- checks robots.txt
- sends a clear User-Agent
- waits at least 3 s between requests to the same host
- caches responses (6 h; event detail pages 7 days) in `.cache/`
- stops at bot challenges; it never tries to get past them

## Output

`listings.json`:

```json
{"generated_at": "...", "sources": [...], "showings": [{
  "id": "ica:1986801A...", "venue": "ICA", "category": "film", "title": "Case 137",
  "match_key": "case 137", "start": "2026-10-25T12:10:00+00:00", "doors": null,
  "runtime_minutes": 115, "lineup": [], "genre": null, "price": null,
  "booking_url": "https://...", "image_url": null, "tags": ["subtitled"]}]}
```

| Field | Notes |
|---|---|
| `category` | `film`, `music`, `theatre`, `comedy` or `dance` |
| `match_key` | Normalised title for grouping the same film across venues. "Preview: Wild Horse Nine + ScreenTalk", "WILD HORSE NINE" and "Wild Horse Nine (2D)" all give `wild horse nine`. `&` becomes `and`. Series prefixes, `+ Q&A`-style extras, anniversaries, formats (2D/4K/35mm/restoration...), years and bracketed alternative titles are dropped. Director's/extended cuts stay distinct. See `match_key` in `listings/text.py`. |
| `start`, `doors` | ISO 8601 with the London offset; `doors` may be null |
| `lineup` | Performers, headliner first; empty for films. Structured where the source has it (Vortex, PizzaExpress, Songkick), otherwise guessed from the title. |
| `genre`, `price`, `runtime_minutes`, `image_url` | null when the source doesn't say |
| `tags` | e.g. `35mm`, `subtitled`, `sold-out`, `season:...`, `time-is-doors`, `manual` |

`status.json` has one entry per venue:

```json
{"venue": "union-chapel", "name": "Union Chapel", "status": "ok",
 "last_success": "2026-10-25T06:04:11+00:00", "listings": 98, "published": 98,
 "manual_listings": 0, "error": null, "source": "..."}
```

`status` is one of:
- `ok`: fetched today.
- `stale`: failed today, so the last good data was reused; `last_success` says from when.
- `failed`: failed with no earlier data to reuse.
- `manual`: the venue only has hand-entered listings.

`summary` counts each status.

## When a venue fails

The error is logged, and shown as an annotation on the Actions run. That
venue's upcoming showings are taken from the freshest earlier data: either the
currently published `listings.json`, or `local/listings.json` from a local run.
The other venues still publish. If nothing at all is collected, the published
files are left alone.

## Hand-entered listings: `manual/`

For venues that can't be fetched, or are fetched only partly, put one JSON
file per venue in `manual/`. See `manual/20261024_README.md` and copy
`manual/20261024_example.json`. On every run:
- the files are merged in
- past showings are dropped
- duplicates of scraped showings are dropped (the scraped one wins)

Pushing a change to `manual/` republishes straight away.

## Venues that block GitHub's servers: `local/`

Some sites treat cloud IP ranges differently from home connections. If
`status.json` shows a venue failing on GitHub, but
`python -m listings collect --venue <slug>` works on your machine:

1. Add the slug to `local/20261024_venues.txt`.
2. Run `scripts/20261024_run_local.sh` once by hand. It collects those venues,
   commits `local/listings.json` and pushes it. The push re-runs the Action,
   which uses this data for venues that fail on GitHub.
3. Schedule it daily at 05:30 London time with a systemd user timer:

   ```bash
   scripts/20261024_install_timer.sh            # install/update and enable
   scripts/20261024_install_timer.sh --remove   # undo
   ```

   The script generates the units with the repo's current path, so re-run it if
   you move the folder. `Persistent=true` runs a missed job at the next boot or
   wake. User timers run only while you're logged in, unless you run
   `sudo loginctl enable-linger $USER`. Logs: `journalctl --user -u london-listings-local`.

   Prefer cron? Add this to `crontab -e`:
   `30 5 * * * "/path/to/repo/scripts/20261024_run_local.sh" >> ~/london-listings-local.log 2>&1`

Currently run locally: The Garden Cinema and The Cinema Museum (both serve a
Cloudflare challenge to GitHub's servers).

## Adding a venue

1. **Look for the most structured source first.** Run
   `python -m listings probe <whats-on URL>` and check the browser's network tab,
   in this order:
   1. a ticketing API the page loads from without a secret key
   2. Event JSON-LD, iCal or RSS
   3. JSON embedded in the page
   4. one server-rendered page with the programme
   5. per-event pages

   Check robots.txt. Don't bypass bot challenges, and don't reuse API keys
   embedded in a venue's page. If the venue is blocked, try Clusterflick (films)
   or a Songkick/DICE venue page (music).

2. **Add one file**, `listings/venues/<slug>.py`. It's discovered automatically.
   Most venues are a few lines on top of a shared source:

   | Source | Base class | Example |
   |---|---|---|
   | Spektrix API | `sources.spektrix.SpektrixVenue` | `ica.py` |
   | Savoy Systems `.dll` page | `sources.savoy.SavoyVenue` | `rio_cinema.py` |
   | The Events Calendar (WordPress) | `sources.tribe_events.TribeEventsVenue` | `cinema_museum.py`, `vortex_jazz_club.py` |
   | Event JSON-LD (DICE, Songkick, ...) | `sources.jsonld.JsonLdEventsVenue` | `moth_club.py`, `kings_place.py` |
   | Clusterflick open data | `sources.clusterflick.ClusterflickVenue` | `curzon_soho.py` |

   For example:

   ```python
   from listings.sources.jsonld import JsonLdEventsVenue

   class MothClub(JsonLdEventsVenue):
       slug = "moth-club"
       name = "MOTH Club"
       page_url = "https://dice.fm/venue/moth-club-43ox"

   VENUE = MothClub()
   ```

   Otherwise, subclass `listings.venues.base.Venue` and implement
   `fetch(client) -> list[Showing]`, as in `garden_cinema.py`. Rules:
   - fetch only through `client`
   - ids are `<slug>:<stable key>`
   - write `start` with `london_iso()`
   - return only upcoming showings
   - set `category`
   - raise an exception if nothing parses, so the run falls back to the last good data

3. **Add a minimum** for the venue to `MIN_SHOWINGS` in `tests/test_venues_live.py`,
   then run `python -m pytest -m network -k <slug>`.
